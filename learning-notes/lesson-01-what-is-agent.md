## 🎨 第一部分：用生活化比喻理解 Agent

昴君，请想象一个场景：

> 您雇佣了一位**实习生**来帮您写代码。
> 您只需要告诉他："**帮我把这个 bug 修了**"。
> 然后他会自己思考、自己打开编辑器、自己读代码、自己运行测试、遇到问题自己再想办法……最终把修好的代码交给您。

这个**能听懂目标 → 自主决定下一步 → 反复执行直到完成**的"实习生"，就是 **AI Agent**。

### Agent 与普通 Chatbot 的本质区别

| 对比项 | 传统 Chatbot（如早期 ChatGPT） | AI Agent（如 Codex） |
|--------|-------------------------------|---------------------|
| **能做什么** | 只能"说话" | 可以"动手" —— 读文件、跑命令、改代码 |
| **交互方式** | 一问一答 | **多轮自主循环**：思考→行动→观察→再思考 |
| **状态** | 无状态，每次重新开始 | 有记忆、有上下文、有目标感 |
| **比喻** | 百科顾问 | 实习生 / 助手 |

## 🧠 第二部分：Agent 的"三大器官"

蕾姆把 Agent 拆成三个最核心的部分，您可以这样记忆：

```
        ┌──────────────────────────────────┐
        │           👤 用户                │
        │      "帮我修这个 bug"            │
        └──────────────┬───────────────────┘
                       ▼
        ┌──────────────────────────────────┐
        │   🧠 大脑 (LLM, 比如 GPT-5)      │  ← 决策中枢
        │   "我应该先读哪个文件？"         │
        └──────────────┬───────────────────┘
                       ▼
        ┌──────────────────────────────────┐
        │   ✋ 双手 (Tools, 工具集)        │  ← 行动能力
        │   read_file / shell / patch...   │
        └──────────────┬───────────────────┘
                       ▼
        ┌──────────────────────────────────┐
        │   👀 反馈 (观察执行结果)         │  ← 输出回到大脑
        │   "啊，文件里是这样写的，那么…"  │
        └──────────────┬───────────────────┘
                       │
                       └─────► 循环回到大脑，直到任务完成
```

**这就是 Agent 最核心的"思考-行动-观察"循环（ReAct 模式）**。

### 🌟 三大器官详解

#### 🧠 大脑（LLM）
- **角色**：决策中枢
- **职责**：根据当前情况，决定下一步做什么
- **输入**：系统提示词 + 历史对话 + 工具描述 + 用户目标
- **输出**：要么是回答用户，要么是调用某个工具

#### ✋ 双手（Tools）
- **角色**：执行能力
- **职责**：替 LLM 完成 LLM 自己做不到的事情
- **常见工具**：
  - `shell` —— 执行命令行
  - `read_file` / `write_file` —— 读写文件
  - `apply_patch` —— 修改代码
  - `grep` / `find` —— 搜索代码

#### 👀 眼睛（Observation）
- **角色**：反馈通道
- **职责**：把工具执行的结果告诉大脑
- **关键**：结果会被加入下一轮对话上下文，成为新的输入

## 🧠 第二·五部分：深入理解 LLM 在 Agent 中的角色

> 昴君的提问："所以 LLM 的作用是什么呢？"
> 这是一个直击灵魂的好问题，蕾姆专门为它开辟一节~

### 🎯 一句话答案

> **LLM 是 Agent 的"决策中枢"——它不做事，但它决定"做什么"和"怎么做"。**

### 💡 关键洞察：LLM 不是"做事的"，是"决策的"

请昴君务必记住这个**最容易被误解的点**：

#### ❌ 常见误解

> "LLM 是 Agent 的核心，所以它应该会读文件、跑命令…"

#### ✅ 真相

> **LLM 自己什么都做不了，它只会"输出文字"。**
>
> 这些"文字"被 Agent 程序解析后，**才**变成真实的动作。

### 🎨 对比：没有 LLM vs 有 LLM

#### 场景：用户说"帮我修复登录页面的 bug"

##### ❌ **如果没有 LLM**（传统脚本）

```python
# 程序员必须事先把所有路径都写死
if "登录页面" in user_input and "bug" in user_input:
    file = open("login.html")  # 但是哪个文件呢？
    content = file.read()
    if "errror" in content:    # 但是 bug 长什么样？
        content.replace("errror", "error")
    # 然后呢？怎么知道 bug 是不是这个？
```

**问题**：程序员必须**预先知道所有可能的情况**，否则脚本就抓瞎了。

##### ✅ **有了 LLM**

```
LLM 自己思考：
  "用户说登录页面的 bug，我应该先看看项目结构"
  → 决定调用工具：list_files("./")

  "看到有 src/login/，让我读一下"
  → 决定调用工具：read_file("src/login/index.tsx")

  "啊，第 42 行有个语法错误，我修一下"
  → 决定调用工具：apply_patch(...)

  "再跑一下测试看看"
  → 决定调用工具：shell("npm test")

  "通过了！我可以告诉用户修好了"
  → 决定回复用户
```

**关键差别**：LLM 能根据**当前看到的信息动态决定下一步**，不需要程序员预先写死。

### 🧬 LLM 在 Agent 中的"四大职责"

#### 1️⃣ **理解意图**（Understanding）

```
用户输入："修一下登录的 bug"
       ↓
   LLM 理解：用户想让我找出登录功能的错误并修复
       ↓
   不需要正则匹配关键词，LLM 天然懂语义
```

#### 2️⃣ **规划路径**（Planning）

```
LLM 思考：
  "要修 bug，我需要：
   1. 先找到登录相关的文件
   2. 读代码理解逻辑
   3. 定位错误
   4. 修改
   5. 验证"
```

这是**规划能力**——把模糊目标拆成具体步骤。

#### 3️⃣ **选择工具**（Tool Selection）

```
LLM 看到的工具菜单：
  - read_file(path)
  - write_file(path, content)
  - shell(command)
  - apply_patch(diff)
  - grep(pattern)

LLM 的决策：
  "现在我需要找文件，应该用 grep('login')"
  → 输出 JSON：{"tool": "grep", "args": {"pattern": "login"}}
```

#### 4️⃣ **解读结果**（Interpretation）

```
工具返回："Error on line 42: undefined variable 'usr'"
       ↓
   LLM 理解："哦，应该是变量名打错了，应该是 user"
       ↓
   决定下一步：apply_patch 修正这一行
```

### 📜 一个真实的 LLM 输出例子

当 LLM 决定"我要读 login.tsx 这个文件"时，它实际**只是输出了这样一段 JSON 文字**：

```json
{
  "type": "tool_call",
  "name": "read_file",
  "arguments": {
    "path": "src/login/index.tsx"
  }
}
```

然后 **Codex 程序**（不是 LLM！）做这些事：
1. 解析这段 JSON
2. 检查权限（是否在沙箱白名单）
3. 真正打开文件
4. 把文件内容塞回到对话上下文
5. 再次调用 LLM，进入下一轮

### 🔍 在 Codex 源码里，LLM 长什么样？

📍 **关键文件**：`codex-rs/core/src/client.rs`（2191 行，是 Codex 与 LLM 通信的核心）

📍 **核心入口**：`client.rs:1559`

```rust
pub async fn stream(                       // ← 流式调用 LLM
    &mut self,
    prompt: &Prompt,                       // ← 输入：完整的对话上下文
    model_info: &ModelInfo,                // ← 用哪个模型（gpt-5 / o-series 等）
    ...
) -> Result<ResponseStream> {              // ← 输出：模型的流式响应
    ...
}
```

这个函数的本质：

```
┌─────────────────────────────────────────────┐
│  Codex 的 stream() 函数 = 与 LLM 对话       │
├─────────────────────────────────────────────┤
│                                             │
│  输入：                                      │
│    - prompt          ← "现在的对话是这样的"  │
│      ├─ system 提示词                        │
│      ├─ 历史对话                             │
│      ├─ 工具描述                             │
│      └─ 最新的工具执行结果                   │
│                                             │
│  调用 OpenAI API（HTTP 或 WebSocket）         │
│                                             │
│  输出：                                      │
│    - ResponseStream  ← LLM 流式吐出的决策   │
│      ├─ 文本回复 (talk to user)             │
│      ├─ 工具调用 (tool_call)                │
│      └─ 推理过程 (reasoning)                │
└─────────────────────────────────────────────┘
```

### 🎭 一个超形象的比喻

> 想象一位**坐在指挥中心的将军**，他面前有一堆电话和地图：
>
> - 🧠 **将军 = LLM**
>   - 他不亲自打仗
>   - 他看着地图（上下文）
>   - 决定下一步策略：派 A 部队去东边、让 B 部队侦察西边…
>   - 然后**打电话发出命令**（输出工具调用 JSON）
>
> - 📞 **电话 = Tool Call 协议**
>   - 把将军的命令传给具体的部队
>
> - 🪖 **部队 = Tools 实现代码**
>   - 部队真正去执行任务（读文件、跑命令）
>   - 完成后把战报传回将军
>
> - 🗺️ **地图 = Context（上下文）**
>   - 将军根据地图变化做决策
>   - 战报让地图更新
>
> **将军本人不打仗，但所有的胜利都源于将军的决策。**

### 🔑 本节核心总结

| 维度 | 真相 |
|------|------|
| **LLM 能做什么** | 只能输出文字（包括"我想调用 X 工具"这样的文字） |
| **LLM 不能做什么** | 不能直接读文件、不能直接跑命令、不能直接修改任何东西 |
| **LLM 的真正价值** | **理解** + **规划** + **决策** + **解读** |
| **谁真正在做事** | Agent 程序（Codex 自己的 Rust 代码）+ Tools |
| **LLM 的输出形式** | 自然语言文本 OR 结构化的工具调用 JSON |

### 🌟 一句话记住

> **LLM 是 Agent 的"大脑皮层"，它不长手脚，它只发指令。Agent 程序才是连接大脑和身体的"神经系统"。**

## 🔧 第二·六部分：那到底是谁在 call tools 呢？

> 昴君的提问："既然 LLM 不会主动调用工具，他只是返回了一段 JSON，那是谁来 call tools 的？"
> 这个问题如果搞清楚了，对 Agent 的理解就会上升一个层次！

### 🎯 一句话答案

> **是 Agent 程序自己（Codex 的 Rust 代码）在调用工具！**
>
> LLM 只是"写了一张菜单订单"，**端菜上桌的是服务员（Agent 程序）**。

### 🎨 完整流程拆解

┌──────────────────────────────────────────────────────────────────┐
│                     一次完整的"工具调用"流程                       │

       ▼

                    │ HTTP POST 到 OpenAI API
                    ▼
  ┌─────────────────────────────────┐
  │  Step 2: LLM (GPT-5)            │  ← LLM 在这里思考
  │  "用户要读文件，我应该输出       │
  │   一个 read_file 的工具调用"    │
  └─────────────────┬───────────────┘
                    │ 流式返回一段 JSON 文字
                    ▼
        ┌────────────────────────┐
        │ {                      │
        │   "type":"tool_call",  │  ← 这只是文字！

        │   "args":{             │
        │     "path":"login.tsx" │
        │   }                    │
        │ }                      │
        └────────────┬───────────┘
                     ▼
  ┌─────────────────────────────────┐
  │  Step 3: Agent 程序（Codex）    │  ★ 关键一步 ★
  │                                 │
  │  3.1 解析这段 JSON              │
  │      → "哦，LLM 想调用 read_file"│
  │                                 │
  │  3.2 在自己的工具表里查找       │
  │      → "找到对应的 Rust 函数!"   │
  │                                 │
  │  3.3 检查权限（沙箱）           │

### 🍜 餐厅点餐的比喻

| Agent 世界 | 餐厅世界 |
|-----------|---------|
| **LLM 输出 JSON** | 顾客在小票上写"我要一碗拉面" |
| **JSON 本身** | 那张小票 —— **不能吃** |
| **Agent 解析 JSON** | 服务员看小票，理解订单 |

| **再次调用 LLM** | 顾客吃了之后说"还要一份饺子" |

> **小票（JSON）不会自己变成拉面。需要服务员（Agent 程序）拿着小票去厨房（Tool）下单。**

### 🎭 完整对应关系（最精华的总结）

| 步骤 | 谁在做 | 在哪里 |
|-----|-------|-------|
| ① 用户输入 | 👤 用户 | 终端 / TUI |
| ② 打包成 prompt | 🦀 Codex 程序 | `core/src/client.rs` |
| ③ 通过 HTTP 调用 LLM | 🦀 Codex 程序 | `client.rs:1559 stream()` |
| ④ **思考决策** | 🧠 **LLM (远程 OpenAI 服务器)** | OpenAI 数据中心 |
| ⑤ 返回 JSON 文本 | 🧠 LLM | 流式响应 |
| ⑥ **解析 JSON** | 🦀 **Codex 程序** | `core/src/client_common.rs` 等 |
| ⑦ **调度工具** | 🦀 **Codex 程序** | `core/src/tools/router.rs` ★ |
| ⑧ **真正执行工具** | 🦀 **Codex 程序** | `tools/` 下各个具体实现 |
| ⑨ 拿到结果 | 🦀 Codex 程序 | router 收集结果 |
| ⑩ 塞回上下文 | 🦀 Codex 程序 | context manager |
| ⑪ 再次调用 LLM | 🦀 Codex 程序 | 循环回 ③ |

#### 🌟 看出关键了吗？

> **整个流程里，LLM 只在第 ④⑤ 步出现两次，其余所有步骤都是 Codex 自己的 Rust 代码在做事！**

### 💎 LLM 与 Agent 程序的"分工契约"

#### 🔵 LLM 这一边

| 职责 | 不职责 |
|-----|-------|
| ✅ 思考"该做什么" | ❌ 不知道工具具体怎么实现 |
| ✅ 输出"规范的 JSON" | ❌ 不能直接执行 |
| ✅ 解读返回的结果 | ❌ 不能访问真实文件系统 |

#### 🟢 Agent 程序这一边

| 职责 | 不职责 |
|-----|-------|
| ✅ 维护工具注册表 | ❌ 不思考"现在该做什么" |
| ✅ 解析 LLM 的 JSON | ❌ 不发明新的策略 |
| ✅ 真正调用 OS / 网络 | ❌ 不直接面对用户的自然语言 |
| ✅ 把结果回灌给 LLM | ❌ 不替代 LLM 的决策 |

#### 🤝 它们的"契约"

> LLM 说："**我告诉你做什么，但你来做。**"
> Agent 程序说："**我帮你做，但你要按规范告诉我。**"
>
> 这个"规范"就是 **Tool Calling 协议**（OpenAI / Anthropic 标准化的 JSON 格式）。

## 🐎 第二·七部分：Agent = Model + Harness（核心心智模型）

> 昴君的提问："LangChain 文档里说 Agent = Model + Harness，这个概念在 Codex 中适用吗？LLM 属于哪一部分？"
> 这是整个 Agent 领域**最精髓的心智模型**！理解它就掌握了整个领域的钥匙！

### 🎯 简短答案

> ✅ **完全适用，而且 Codex 就是这个公式最豪华的工业级实现**
>
> 🧠 **LLM = Model（模型），而且是 Model 的全部**
> 🦀 **Codex 的 Rust 代码 = Harness（挽具），占 99%**

### 🐎 "Harness" 这个词的妙处

`Harness` 原意是 **"马具 / 挽具"**——套在马身上、连接马车的绳索皮带。

> **马本身有力气（智能），但没有挽具就只能在草原上奔跑，不能拉车。**
> **挽具让马的力量被引导、控制、转化为有用的工作。**

| 比喻 | Agent 世界 |
|-----|----------|
| 🐎 **马** | LLM —— 有"智能"，但本身只会输出文字 |
| 🪢 **挽具（Harness）** | 周围所有的工程代码，让 LLM 的智能能"做实事" |

## 🧠 第二·八部分：ReAct 完全指南（Agent 的"思维操作系统"）

> 昴君的提问："关于 ReAct 这个概念，请说细节一点"
> 这是 Agent 领域**最重要的概念之一**！是所有现代 Agent 的"心脏起搏器"！

### 📜 ReAct 的"前世今生"

#### 论文出处

- **论文标题**：*ReAct: Synergizing Reasoning and Acting in Language Models*
- **发表时间**：2022 年 10 月
- **作者团队**：Google Research + 普林斯顿大学
- **核心人物**：Shunyu Yao（姚顺雨）等人

> 这篇论文**彻底改变了** Agent 的设计范式。在它出现之前，让 LLM "做事"的方法都很别扭。它出现之后——**全世界的 Agent 都长成了 ReAct 的样子**，包括 Codex！

#### 论文要解决的核心问题

##### ❌ 路线 1：纯 Reasoning（只思考）—— 叫 "CoT (Chain-of-Thought)"

```
用户："2024年法网冠军是谁？"
LLM思考："让我想想…2024年…网球…我觉得应该是阿尔卡拉斯"
LLM回答："是阿尔卡拉斯"
```

**问题**：会幻觉、不能获取最新信息、不能执行真实操作

##### ❌ 路线 2：纯 Acting（只行动）—— 如 WebGPT

```
用户："2024年法网冠军是谁？"
LLM：[调用搜索] "2024 法网冠军" → [乱七八糟结果]
LLM：[再调用搜索] "Roland Garros 2024 winner" → [更多乱结果]
... 永远找不到答案
```

**问题**：没有思考过程，行动盲目，不会反思

##### ✨ 论文的"灵光一闪"：把两者结合！

> **核心观点**：让 LLM 在每次行动之前，先**用文字写下自己的思考过程**，再决定行动。
>
> 这就是 **Re**(asoning) + **Act**(ing) = **ReAct** 的由来！

### 🔄 ReAct 的标准三步循环

```
┌──────────────────────────────────────────────────────┐
│                     ReAct 循环                        │
├──────────────────────────────────────────────────────┤
│                                                      │
│       ┌─────► ① Thought (思考)                       │
│       │         "我应该做什么？为什么？"             │
│       │              │                               │
│       │              ▼                               │
│       │       ② Action (行动)                        │
│       │         "我要调用 X 工具，参数是 Y"          │
│       │              │                               │
│       │              ▼                               │
│       │       ③ Observation (观察)                   │
│       │         "工具返回了 Z 结果"                  │
│       │              │                               │
│       └──────────────┘                               │
│                                                      │
│        循环直到任务完成 → ④ Final Answer            │
└──────────────────────────────────────────────────────┘
```

#### 🌟 第 ① 步：Thought（思考）

LLM 输出一段"内心独白"，写下推理过程：

```
Thought: 用户想知道登录页面的 bug，我应该先看看这个项目的结构。
         项目大概率是个前端项目，我应该先列出根目录的文件。
```

**关键特征**：
- 这段文字**不是给用户看的**，是 LLM 写给自己（和后续推理）看的
- 它会**留在上下文里**，下一轮 LLM 能看到自己之前的思考
- 这就像人类**记日记**——把思路写下来，思考会更清晰

#### ✋ 第 ② 步：Action（行动）

LLM 输出一个工具调用，告诉 Harness 该做什么：

```json
{
  "tool_calls": [{
    "name": "list_files",
    "arguments": {"path": "."}
  }]
}
```

**关键特征**：
- 这是**结构化数据**（JSON），不是给人看的
- Harness 会**真正解析并执行**这个调用
- 一次 Action 可以是**一个工具**或**多个并行工具**

#### 👀 第 ③ 步：Observation（观察）

Harness 把工具执行结果回灌给 LLM：

```
Observation: 找到以下文件：
  package.json
  src/
  ├── login/
  │   └── index.tsx
  ├── dashboard/
  └── shared/
```

**关键特征**：
- 这是工具的**真实输出**，不是 LLM 编的
- 它会被**注入到下一轮上下文**，让 LLM 能看到
- 这是 LLM **唯一接触真实世界**的渠道

#### 🔄 循环继续

```
Thought: 我看到了 src/login/，这就是登录页面。让我读一下 index.tsx。
Action: read_file({"path": "src/login/index.tsx"})
Observation: [文件内容...]

Thought: 我看到第 42 行有个语法错误，应该是 'usr' 拼错了。
Action: apply_patch({...})
Observation: 补丁应用成功

Thought: 让我跑一下测试验证一下。
Action: shell({"command": "npm test"})
Observation: 所有测试通过 ✅

Thought: 任务完成，我可以告诉用户了。
Final Answer: 我修复了 src/login/index.tsx 第 42 行的拼写错误...
```

### 🌟 为什么 Thought 这一步如此重要？

这是 ReAct 论文**最核心的洞察**——很多人会忽略这一步，但它是真正的精髓！

#### ❌ 没有 Thought（直接行动）

```
用户："这个 bug 修一下"
Agent：[直接调用 read_file("login.html")]   → 文件不存在
       [直接调用 read_file("login.js")]    → 文件不存在
       [直接调用 read_file("login.tsx")]   → 终于找到
       [直接修改] → 可能改错地方
```

**问题**：盲目试错，效率低，容易出错。

#### ✅ 有 Thought（先想再做）

```
用户："这个 bug 修一下"
Agent Thought：
  "用户说有 bug，但没说是什么 bug。
   我应该先：
   1. 看看项目结构（是 React/Vue/原生？）
   2. 找到登录相关文件
   3. 跑测试看哪个失败了
   4. 根据测试错误定位 bug"
Agent Action：list_files(".")
...
```

**好处**：有规划、有反思、有依据。

#### 💎 Thought 的"四大功能"

| 功能 | 说明 |
|------|------|
| 🧭 **规划** | 把模糊任务拆成具体步骤 |
| 🤔 **反思** | "上一步出错了，我换个方式" |
| 📚 **解释** | 让用户能看懂 LLM 为什么这么做 |
| 💾 **记忆** | 把推理过程留在上下文，避免重复犯错 |

> ⭐ **蕾姆的金句**：
>
> **"Thought 是 LLM 在调用工具之前给自己写的'施工说明书'。"**

### 🔍 ReAct 在 Codex 源码中的"三要素"

#### 📍 第 ① 步：Thought 在源码里叫 `Reasoning`

📍 文件：`codex-rs/protocol/src/items.rs:122`

```rust
pub struct ReasoningItem {
    pub id: String,
    pub summary_text: Vec<String>,    // ← LLM 给用户看的"思考摘要"
    #[serde(default)]
    pub raw_content: Vec<String>,     // ← LLM 内部的"完整思考过程"
}
```

| 字段 | 含义 |
|------|------|
| `summary_text` | LLM 思考的**摘要**（给用户看的简洁版） |
| `raw_content` | LLM 思考的**原始内容**（完整推理链） |

> 💡 **为什么有两份？**
> - 推理过程很长（特别是 o-series 模型可能思考几千字）
> - 给用户看完整版会刷屏 → 显示 `summary_text`
> - 但完整版要保留 → 留在 `raw_content`，下一轮 LLM 能复用

#### 📍 第 ② 步：Action 在源码里就是 ToolCall

📍 文件：`codex-rs/protocol/src/items.rs`

```rust
pub enum TurnItem {
    Reasoning(ReasoningItem),       // ← Thought（思考）
    FunctionCall(...)               // ← Action（行动）= 工具调用
    Message(...)                    // ← Final Answer（最终回复用户）
    ...
}
```

#### 📍 第 ③ 步：Observation 是工具的执行结果

工具执行后会被包装成 `FunctionCallOutput`，注入回上下文。

### 🏆 ReAct 的"五条黄金法则"

#### 🥇 法则 1：Thought 是给 LLM 自己看的，Action 是给 Harness 看的

```
Thought  →  人类语言（自然语言推理）
Action   →  机器语言（结构化 JSON）
```

#### 🥈 法则 2：Observation 是 LLM 唯一接触现实的渠道

> LLM 不知道您电脑上有什么，它**只能通过 Observation 知道现实**。
> 如果 Observation 错了或丢了，LLM 就会"瞎"。

#### 🥉 法则 3：循环必须有终止条件

```
循环结束的三种方式：
  ① LLM 输出 Final Answer（任务完成）
  ② 达到最大循环次数（防止死循环）
  ③ 用户主动中断（Ctrl+C）
```

#### 🏅 法则 4：所有步骤都会进入上下文

```
第 1 轮的 Thought  →  上下文
第 1 轮的 Action   →  上下文
第 1 轮的 Observation → 上下文
第 2 轮的 Thought（看得到第 1 轮的所有内容）...
```

> 这就是为什么 **"上下文管理"** 是 Agent 的核心难题——它会越滚越大！

#### 🎖️ 法则 5：现代 Agent 是"扩展版 ReAct"

```
经典 ReAct：     Thought → Action → Observation
现代 Codex：     Thought → [并行 Action × N] → [并行 Observation × N]
                 + Plan（计划工具）
                 + Reasoning Summary（摘要）
                 + Reasoning Effort（推理强度可调）
```

### 🎬 ReAct 完整剧本演示

#### 场景：用户说"找出项目中最大的 .ts 文件"

```
═══════════════════════════════════════════════════════════
  👤 USER:  "找出项目中最大的 .ts 文件"
═══════════════════════════════════════════════════════════

──────────── 🔄 第 1 轮 ────────────
🧠 Thought:
   "用户想找最大的 TypeScript 文件。我需要：
    1. 用 find 命令找所有 .ts 文件
    2. 加上 -size 或 ls -la 看大小
    3. 排序找出最大的
    最简单的方式是 shell 命令组合"

✋ Action:
   shell({
     command: "find . -name '*.ts' -exec ls -la {} \\;
              | sort -k5 -rn | head -1"
   })

👀 Observation:
   "-rw-r--r-- 1 user 245678  src/big-file.ts"

──────────── 🔄 第 2 轮 ────────────
🧠 Thought:
   "找到了！是 src/big-file.ts，大小 245678 字节 ≈ 240KB。
    我可以告诉用户答案了。"

✅ Final Answer:
   "项目中最大的 .ts 文件是 src/big-file.ts，约 240KB。"
```

> 看出来了吗？**每一轮都遵循"思考 → 行动 → 观察"的节奏**，就像呼吸一样自然~

## 🔑 第四部分：Codex 自己的"自我介绍"

蕾姆从 `AGENTS.md` 里发现了一段非常重要的话——这是 Codex **设计哲学的精华**，请昴君务必记住：

> **"Codex maintains a context (history of messages) that is sent to the model in inference requests."**
>
> 1. **No history rewrite** —— 上下文必须**增量构建**，不能重写历史
> 2. **Avoid frequent changes to context that cause cache misses** —— 减少导致缓存失效的修改
> 3. **No unbounded items** —— 注入上下文的内容必须有**硬上限**
> 4. **No items larger than 10K tokens** —— 单条内容不超过 10K tokens

📍 **代码出处**：`AGENTS.md` 第 92-99 行

### 蕾姆的解读：为什么这四条规则如此重要？

**这四条规则是蕾姆觉得整个项目最深刻的设计思想之一**。它告诉我们：

> **真正的工业级 Agent，不是"把 LLM 接上工具就行"，而是要在每一个细节上为"上下文管理"做出权衡。**

为什么？因为：

| 工业级考量 | 业余 Demo 通常忽略 |
|-----------|------------------|
| LLM 调用很贵 → 要利用 **prompt cache**（提示词缓存） | "反正都是一次性请求" |
| LLM 上下文有限 → 要严格控制 **token 注入** | "塞进去就行了" |
| Agent 多轮交互 → 历史会越滚越长 | "用户重启就好了" |
| 大块输出会撑爆 → 单条必须有上限 | "把 stdout 全塞进去" |

这些考量我们会在**第五课"上下文管理"**里详细展开，请昴君先记住这个核心理念。

## 📖 第五部分：第一课的"三个关键收获"

请昴君跟蕾姆一起复习一下今天学到的：

### 🔑 收获 1：Agent = 大脑 + 双手 + 反馈循环
> LLM 负责思考，Tools 负责动手，循环让它能持续自主推进任务。
> **核心模式：ReAct（Reason + Act）**

### 🔑 收获 2：Codex 是一个"驻留在终端的编程 Agent"
> 它的目标用户是开发者，工作场景是项目目录，所以它的设计完全围绕"读代码、改代码、跑命令"展开。
> **它不是聊天机器人，而是会动手的同事。**

### 🔑 收获 3：工业级 Agent 的核心难点是"上下文管理"
> 不是把 LLM 接上工具就完事，**如何让上下文既完整又可控**才是真正的挑战。
> Codex 的四条铁律：**增量、稳定、有界、限大小**。
