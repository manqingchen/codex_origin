# 📝 Q1：什么是 Agent？与大模型有什么本质不同？

> **难度**：⭐⭐⭐⭐⭐
> **频率**：极高（美团、字节、腾讯都问过）
> **类型**：基础概念题（用来筛掉只会调 API 的候选人）

---

## 💡 简要回答模板（30 秒口述版）

```
"Agent 本质上是一个能【自主完成目标】的 AI 系统。

跟传统 AI 最核心的区别在【自主性】和【能行动】：

• 传统 AI = 一问一答的【问答机器】，每次独立、被动响应
• Agent = 有【规划能力】，能拆解任务、调用工具、访问记忆、
          感知环境，一步步执行直到完成目标

它不只是【输出文字】，而是【真的能做事】。"
```

---

## 📖 详细回答框架（2-3 分钟版）

### 🎯 步骤 1：先说大模型的局限性

```
"你直接调用 GPT 的 chat 接口，它本质上是个【问答机器】——

• 你给它一个输入，它给你一个输出，然后结束
• 即使多轮对话，也只是在【当前上下文】里被动响应
• 它不会主动做任何事
• 它不知道自己上一步做了什么、下一步该做什么

可以把它想象成一个【只会答题的人】——
你说一句它答一句，但让它【自己去查资料再来汇报】，
它完全做不到。"
```

### 🎯 步骤 2：再说 Agent 的运作闭环

```
"Agent 有一个核心运作闭环：

【感知 → 规划 → 行动 → 再感知】

你给它一个目标（比如【帮我调研竞品然后整理成报告】），
它不是直接输出一段文字了事，而是：

1. 先【拆解任务】：要搜索哪些关键词、要访问哪些网站
2. 然后【一步步执行】：每一步的结果又反馈回来
3. 指导【下一步怎么做】

直到完成整个目标。"
```

### 🎯 步骤 3：讲清楚支撑 Agent 的三件事

```
"这种能力背后，有三件核心的事在支撑：

第一件：工具调用（Tool Use）
   关键：不是模型自己执行，是模型【告诉系统该调什么】，
         你的代码去真正执行，结果反馈给模型。
         模型始终只是【大脑】，不是【手脚】。

第二件：记忆机制
   • 短期记忆：当前任务的中间状态
   • 长期记忆：跨任务的用户偏好、历史操作
   让 Agent 执行复杂任务时保持连贯性。

第三件：多步推理 + 自我纠错
   某一步失败 → 感知失败 → 分析原因 → 换种方式重试
   而不是直接崩掉。"
```

### 🎯 步骤 4：用一个具体场景收尾

```
"举一个最直观的场景：

让普通 LLM【帮我发一封天气播报邮件】
  → 它只能告诉你【你可以这样写代码...】

让 Agent 做同样的事
  → 它会【真的去调天气 API、拿数据、写邮件内容、调发送接口】
  → 整个过程自动完成

这就是本质区别：【从生成文字，到执行任务】。"
```

# 📝 Q2：大模型是怎么调用外部工具的？

> **难度**：⭐⭐⭐⭐⭐
> **频率**：极高（字节一面就问，答错就挂）
> **类型**：核心机制题

---

## 💡 标准回答

```
"关键认识：模型本身【不执行任何代码】。

整个流程是这样的：

【第 1 步：注册工具】
   提前告诉 LLM "我有哪些工具可用"
   每个工具包含 3 件事：
   • 名字（name）
   • 描述（description）
   • 参数 schema（JSON Schema）

【第 2 步：LLM 决策】
   LLM 看用户需求 + 工具列表
   决定"该用哪个工具 + 参数填什么"
   以 JSON 格式输出 FunctionCall

【第 3 步：Harness 执行】
   我们的代码读 LLM 输出的 JSON
   根据名字找到对应的工具实现
   传入参数，真正执行
   把结果反馈给 LLM

【第 4 步：LLM 继续】
   LLM 看到工具结果
   决定"下一步做什么"
   可能继续调工具，也可能给最终答案

这种【决策和执行分离】的思想，是理解工具调用最核心的一点。"
```

---

## 🔍 Codex 源码对应

```
第 1 步：工具注册
   → codex-rs/core/src/tools/registry.rs
   → ToolRouter 把所有工具登记

第 2 步：LLM 决策
   → 输出 ResponseItem::FunctionCall
   → 包含 name + arguments

第 3 步：Harness 执行
   → codex-rs/core/src/session/turn.rs:1975
   → handle_output_item_done
   → ToolCallRuntime 派发到对应 handler
   → 异步执行（in_flight 队列）

第 4 步：结果回填
   → drain_in_flight 收集结果
   → record_conversation_items 写入 history
   → 下一轮 LLM 自然看到
```

# 📝 Q3：大模型知识过时了怎么解决？

> **难度**：⭐⭐⭐⭐
> **频率**：高（字节二面）
> **类型**：应用方案题

---

## 💡 标准回答

```
"有 3 个主流方案，各有适用场景：

【方案 1：微调（Fine-tuning）】
   • 用新数据重新训练模型
   • 优点：模型【内化】知识，回答快
   • 缺点：成本高、迭代慢、不能实时更新
   • 适用：相对稳定的领域知识

【方案 2：RAG（Retrieval-Augmented Generation）】⭐ 主流
   • 把知识存进向量数据库
   • 每次请求时【检索相关内容】塞进 prompt
   • 优点：实时更新、成本低、可控
   • 缺点：依赖检索质量、prompt 会变长
   • 适用：大多数知识更新场景

【方案 3：工具调用（联网搜索）】
   • 给 Agent 配个 web_search 工具
   • LLM 自己决定什么时候去搜索
   • 优点：最实时、零成本维护知识库
   • 缺点：依赖搜索质量、可能慢
   • 适用：突发新闻、实时数据

实际项目中通常【组合使用】：
   RAG（内部知识库）+ 工具调用（外部搜索）+ 偶尔微调"
```

---

## 🔍 Codex 源码对应

```
Codex 实际上用了【方案 2 + 方案 3 的组合】：

方案 2（RAG-like）：
   → AGENTS.md、CLAUDE.md 等上下文文件
   → 每次 turn 把项目知识注入 prompt

方案 3（工具调用）：
   → web_search 工具
   → MCP 工具（外部知识源）
```

# 📝 Q4：MCP 协议是什么？跟 Agent 开发什么关系？

> **难度**：⭐⭐⭐⭐⭐
> **频率**：极高（腾讯一面必问）
> **类型**：协议理解题

---

## 💡 标准回答

```
"MCP 全称是 Model Context Protocol（模型上下文协议）——
是 Anthropic 在 2024 年底推出的【Agent 工具生态】标准协议。

要理解 MCP，先理解它解决了什么问题：

【问题】：以前每个 Agent 框架都要自己写工具
   • LangChain 写一套
   • Cursor 写一套
   • Codex 写一套
   • 同一个 GitHub 工具被实现了 N 次
   • 工具不能跨 Agent 复用

【MCP 的解决方案】：
   定义一套【标准接口】
   工具开发者【一次实现】
   所有遵守协议的 Agent 都能用

【MCP 的 3 个核心概念】：

1. MCP Server：
   工具实现方。比如 GitHub MCP Server、Filesystem MCP Server
   暴露一组工具 + 资源 + prompt

2. MCP Client：
   Agent 框架。比如 Codex、Claude Desktop
   连接 MCP Server，把工具暴露给 LLM

3. MCP Protocol：
   两者之间的通信协议（基于 JSON-RPC）
   定义如何注册工具、调用工具、传递结果

【价值】：
   ✅ 工具生态化（一次实现，到处使用）
   ✅ Agent 可插拔（用户自己选要哪些工具）
   ✅ 解耦工具开发者和 Agent 开发者"
```

---

## 🔍 Codex 源码对应

```
Codex 是【MCP Client】的实现：

→ codex-rs/core/src/mcp.rs (MCP 客户端核心)
→ codex-rs/core/src/tools/handlers/mcp.rs (MCP 工具适配)
→ codex-rs/mcp-server/ (Codex 自己也能作为 MCP Server)

Codex 启动时：
   1. 读取配置里的 MCP Server 列表
   2. 跟每个 Server 建立连接
   3. 拉取它们的工具清单
   4. 注册进 ToolRouter

LLM 看到的工具列表 = 内置工具 + 所有 MCP 工具
```

# 📝 Q5：A2A 和 MCP 的区别？

> **难度**：⭐⭐⭐⭐
> **频率**：中（阿里、字节）
> **类型**：协议对比题

---

## 💡 标准回答

```
"A2A 全称 Agent-to-Agent（Google 在 2025 年推的协议）。
MCP 全称 Model Context Protocol（Anthropic 在 2024 年推的）。

两者解决【完全不同】的问题：

┌────────────────────────────────────────────────────────┐
│              MCP                       A2A              │
│  ─────────────────────────────────────────────────     │
│  谁跟谁通信     Agent ↔ 工具          Agent ↔ Agent     │
│                                                         │
│  解决问题        工具生态化            Agent 协作        │
│                                                         │
│  类比          USB 接口（接外设）     电话（Agent 之间通话）│
│                                                         │
│  例子          GitHub MCP Server      多 Agent 系统      │
│                                                         │
│  推出方        Anthropic              Google            │
└────────────────────────────────────────────────────────┘

简单说：
• 想让 Agent 用上某个工具？ → 用 MCP
• 想让多个 Agent 协作？ → 用 A2A

两者【互补不冲突】——
一个完整的 Agent 系统可能：
   通过 MCP 接入各种工具，
   通过 A2A 跟其他 Agent 协作完成大任务。"
```

---

## ⚠️ 踩坑点

```
❌ "不都是协议吗？"
   → 阿里技术官当场凉

✅ 关键差别：【通信对象不同】
   • MCP = Agent ↔ Tool
   • A2A = Agent ↔ Agent
```

# 📝 Q6：Agent 的自主性体现在哪里？什么是自我纠错？

> **难度**：⭐⭐⭐⭐⭐
> **频率**：高
> **类型**：架构设计题

---

## 💡 标准回答

```
"Agent 的自主性体现在【3 个层面】：

【层面 1：任务拆解】
   用户给【高层目标】（比如"调研竞品"）
   Agent 自己拆成【子任务】（搜索 → 访问网站 → 整理 → 总结）
   而不需要用户一步步告诉它怎么做

【层面 2：工具选择】
   Agent 自己决定【什么时候用哪个工具】
   不是【硬编码顺序】，而是【根据当前状态判断】

【层面 3：自我纠错】 ← 重点
   工具失败时——
   传统程序：抛异常崩溃
   Agent：
   1. 感知失败（看到 error）
   2. 分析原因（LLM 推理）
   3. 决定下一步（换工具？换参数？放弃？）
   4. 重试或汇报

举个例子：
   Agent 想读 README.md 文件
   → 工具返回"文件不存在"
   → Agent 自动尝试 readme.md（小写）
   → 还失败
   → Agent 列出当前目录看看
   → 发现是 README.rst
   → 改用 read 工具读取
   → 成功！

【整个过程没有人工干预】，这就是自主性。"
```

---

## 🔍 Codex 源码对应

```
自我纠错在 Codex 里的实现：

1. 工具失败【不会让 Codex 崩溃】
   → 失败信息被【写进 history】
   → 作为 FunctionCallOutput 的一部分

2. 下一轮 LLM 看到错误
   → 自然在 prompt 里看到 "tool failed: file not found"
   → LLM 自己决定下一步

3. 这就是 ReAct 循环里的 Observe 步骤
   → codex-rs/core/src/session/turn.rs:1988
   → needs_follow_up |= true (工具调用就要继续)
```

---

## 🎯 加分点

```
✅ 主动提【失败优雅处理】：
```
