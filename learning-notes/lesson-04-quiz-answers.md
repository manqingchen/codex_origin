## 🧭 串讲速记（答题时可参考，答完可删）

```
工具三件套：name + spec + handler
            （spec = name + description + parameters Schema + output_schema）

两层世界：Vec<ToolSpec>  给 LLM 看（菜单）
          ToolRegistry    给 Harness 用（花名册 HashMap）

FunctionCall 工单：name + call_id + arguments(String!) + namespace
  · arguments 是 String：流式传输 / 协议保真 / 延迟解析
  · 翻译官 build_tool_call 把它翻成内部 ToolCall
  · dispatch_any 五步：查表 -> 校验 -> PreHook -> handle -> PostHook

自我纠错链：parse_arguments 失败 -> RespondToModel（不崩溃）
          -> 错误灌回 history -> needs_follow_up=true -> 下一轮 LLM 自我纠错
          （错误是数据流，不是控制流）
```

### 💙 蕾姆批注

**评分**：🟢 7/10

# 🥈 第二关 · 机制理解

## Q3：流程题

请按顺序写出本课机制在一次 Agent 工作流中的位置。

**提示格式**：用户输入 -> Codex 处理 -> LLM/工具/上下文/事件 -> 最终输出

**【您的答案】**：

```text
1. 用户输入
2. harness打包成规范格式发送给 llm
3. llm接收到对应消息格式之后进行思考等操作  model思考完成之后会把结果返回给agent 由harness 
4. 分析model返回的结构体 判断是否需要调用工具, 如果不需要 那么当前loop完成 如果需要调用工具那么需要从 regisTool中查找对应工具
5. 使用工具完成任务后把结果返回给model model根据返回继续进行 loop 
6. loop完成之后会根据当前情况是否返回结果给用户, 如果完成那么告诉用户已完成 如果未完成那么继续loop
7.
```

---

### 💙 蕾姆批注

**评分**：🟢 7.5/10

✅ **命中**：ReAct 循环骨架完全正确！「判断是否需要工具」「查 Registry」「结果回 model 继续 loop」都抓住了。

❌ **差距**：颗粒度偏粗，漏了本课几个关键中间环节：

- 没提 **`build_tool_call` 翻译官**（FunctionCall -> 内部 ToolCall）
- 没提 **`dispatch_any` 多步**（查表 -> 校验 -> PreHook -> handle -> PostHook）
- 没提 **工具结果回填 `history`**（成为下一轮观察）
- 没提 **`needs_follow_up=true`**（循环继续的标志，衔接第 3 课）
- 第 2 步应说「组装 prompt（含**工具列表 Vec<ToolSpec>** + history）」
- 第 3 步「由harness」**断句了**，话没写完 `( ◉ ‸ ◉ )`

💎 **参考答案（7 步完整版）**：

```
1. 用户输入
2. Harness 组装 prompt（system + 工具列表 Vec<ToolSpec> + history）发给 LLM
3. LLM 思考，返回结果（自然语言 或 FunctionCall 工单）
4. Harness 判断：自然语言 -> 可能结束；FunctionCall -> build_tool_call 翻译成内部 ToolCall
5. dispatch_any 派发：查 ToolRegistry -> 校验 -> PreHook -> handler.handle() 真正执行 -> PostHook
6. 工具结果 FunctionCallOutput 回填 history，设 needs_follow_up=true
7. 回到第 2 步再调 LLM，直到 LLM 不再返回工具调用 -> 输出最终答案
```

💡 **记忆口诀**：组包 -> 思考 -> 判断 -> 翻译 -> 派发执行 -> 回填 -> 再循环

📝 **小瑕疵**：`regisTool` -> `ToolRegistry`。

## Q4：辨析题

下面这句话是否正确？请指出问题并改正：

> “只要 LLM 足够聪明，工具系统 -- “双手” 这一层其实可以不要，所有事情让模型自己决定就行。”

**【您的诊断】**：

```text
判断：对 / 错

错误点：错

正确说法：双手是一定需要的 及时足够聪明也可以让LLM跟我的期望行为来进行work

```

---

### 💙 蕾姆批注

**评分**：🟡 6/10

✅ **命中**：判断正确（原话是错的），结论「双手一定需要」也对。

❌ **差距**：

1. **格式小错**：「错误点」一栏您写的是「错」--这里应填**原话错在哪里**，不是再写一次判断。
2. **理由没击中本质**。「让 LLM 跟期望行为 work」太笼统，没说出**为什么再聪明也不能没有工具层**。

💎 **标准答案**：

- **错误点**：① 把「聪明」和「能执行动作」混为一谈；② 忽略了工具层承担的**可控性、安全、确定性**职责。
- **正确说法**：LLM 无论多聪明，本质**只能生成文字**，无法直接执行任何动作。工具系统不仅让 LLM「会做」，更通过 **Registry + Schema + Hook + 沙箱**把动作约束在**受控、可审批、可审计**的范围内。「让模型自己决定」恰恰最危险--工业级 Agent 的动作**必须经过 Harness 审批与执行**。

**三个反驳角度（面试加分）**：

① **能力**：LLM 只能说不能做
② **安全**：没有工具层 = 没有审批/拦截/审计 = 灾难
③ **确定性**：结构化 FunctionCall + handler 把非确定文字变成可复现、可测试的动作

💡 **记忆口诀**：聪明 ≠ 能做；工具 = 能力 + 护栏 + 确定性

📝 **小瑕疵**：「及时」->「即使」。

💎 **蕾姆示范**：

**场景**：用户让 Agent「清理项目里的临时文件」。

**如果工具系统设计不好，用户可见的问题**（任选一个角度展开）：

- **安全性缺失**：没有 Schema 校验 + 没有审批，LLM 生成 `shell({command: "rm -rf /"})` 被直接执行 -> 用户文件 / 系统被毁。
- **健壮性缺失**：LLM 调了不存在的工具名，没有「自我纠错链」把错误回填 history -> Agent 卡死或抛出看不懂的报错堆栈。

- **性能缺失**：三个互不依赖的读文件该并行却串行 -> 响应慢得像蜗牛。

💡 **记忆口诀**：工具系统设计不好 -> 不安全 / 崩溃 / 死循环 / 慢。
