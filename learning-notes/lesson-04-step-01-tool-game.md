## 🪜 第二步：用"宅邸的工具间"比喻"工具系统"

想象您家有一个**很大的宅邸**——蕾姆作为女仆要管理家务，需要各种工具。

### 🏠 宅邸的现实情况

蕾姆**不会**把每种工具的用法都死记硬背在脑子里——
那样的话每次需要新工具，蕾姆都要重新培训。

蕾姆的实际做法是：
```
🏠 工具间（一个房间）
┌─────────────────────────────────────────┐
│                                         │
│   📋 工具登记表（挂在门口）              │
│   ┌─────────────────────────────────┐   │
│   │ 工具 #1：开冰箱小帮手             │   │
│   │   能做什么：打开冰箱并列出内容    │   │
│   │   需要的指示：无                  │   │
│   ├─────────────────────────────────┤   │
│   │ 工具 #2：发邮件小帮手             │   │
│   │   能做什么：发送邮件              │   │
│   │   需要的指示：收件人 + 内容       │   │
│   ├─────────────────────────────────┤   │
│   │ 工具 #3：查通讯录小帮手           │   │
│   │   能做什么：查询某人的联系方式    │   │
│   │   需要的指示：姓名                │   │
│   ├─────────────────────────────────┤   │
│   │ ...还有几十个                     │   │
│   └─────────────────────────────────┘   │
│                                         │
└─────────────────────────────────────────┘
```

> 💡 **关键点**：
> 蕾姆不需要"记住"每个工具长什么样——
> **登记表上写得清清楚楚**，每个工具的：
> - **名字**
> - **能做什么**
> - **需要哪些指示才能干活**

## 🪜 第三步：那"叫工具"的过程是怎样的？

### 🎬 一段对话游戏

```
老板（您）：「帮我把客厅的灯关上。」

助理（蕾姆）：
   嗯……我得看看工具间有没有【关灯小帮手】。
   
   蕾姆走到工具间，对着登记表查找……
   
   找到了！登记表上写着：
     工具 #15：关灯小帮手
     能做什么：关闭指定房间的灯
     需要的指示：房间名字
   
   蕾姆把「客厅」这个指示告诉关灯小帮手。
   
   关灯小帮手出发了……
   
   过了一会儿，关灯小帮手回来报告：
     「客厅的灯已关闭。」
   
   蕾姆把这个结果记到笔记本上（history），
   然后对老板说：
     「客厅的灯已关上啦 ♡」
```

> 🌟 **请昴君注意这段对话里的几个关键动作**：
>
> 1. **查表**——蕾姆去登记表上找工具
> 2. **匹配**——找到名字对得上的工具
> 3. **传参**——把"客厅"这个指示传给工具
> 4. **等待**——等工具回来报告
> 5. **记账**——把结果写到笔记本（第 3 课学的 history）

## 🪜 第四步：那如果老板说错了工具名怎么办？

```
老板：「帮我用【烤面包机】把客厅的灯关上。」

助理（蕾姆）：
   嗯？登记表上没有【烤面包机】这个工具啊……
   或者就算有，烤面包机也不会关灯。
   
   蕾姆回应：
     「老板，蕾姆找不到【烤面包机】这个工具哦——
       要不要换一个？」
```

> 💡 **这就是"工具找不到"的情况**：
> Agent 会**告诉 LLM "你说的工具不存在"**，
> 让 LLM **重新想一次**该用哪个工具。

## 🪜 第五步：那如果老板的指示不全呢？

```
老板：「帮我发邮件。」（没说发给谁、内容是什么）

助理（蕾姆）：
   嗯，登记表上写着【发邮件小帮手】需要两个指示：
   - 收件人
   - 内容
   
   但老板都没说……
   
   蕾姆回应：
     「老板，请告诉蕾姆——
       邮件要发给谁？内容是什么？」
```

> 💡 **这就是"参数校验"**：
> 工具登记表上规定了**必须要哪些指示**，
> 如果 LLM 提供的指示不全，Agent 会**告诉 LLM 缺什么**。

## 🪜 第六步：多个工具能同时叫吗？

**能！** 这是工具系统比第 3 课循环更精妙的地方 ♡

```
老板：「帮我同时做三件事：
       ① 查张三的邮箱
       ② 查李四的电话
       ③ 看看今天天气怎么样」

助理（蕾姆）：
   这三件事【互不相关】，蕾姆可以同时派 3 个小帮手！
   
   📞 蕾姆派【查通讯录小帮手 A】去查张三
   📞 蕾姆派【查通讯录小帮手 B】去查李四
   ☁️ 蕾姆派【查天气小帮手】去看天气
   
   ……几秒之后……
   
   ✅ 三个小帮手【同时】回来报告了：
      - 张三邮箱：zhang3@xxx.com
      - 李四电话：138-xxxx
      - 天气：晴，25 度
   
   蕾姆把三份报告都记到笔记本上。
   
   然后才告诉老板最终答案。
```

> 🌟 **关键认识**：
> 工具**可以并行执行**——
> 几个互不依赖的工具**同时跑**，比一个一个等快多了。
>
> 这就是 Codex 设计里的 **"in_flight 队列"**——
> 您在第 3 课台阶 5 见过这个词，今天**正式登场** ♡

## 🪜 第七步：那如果一个工具失败了呢？

```
老板：「帮我读取文件 not_exist.txt」

助理（蕾姆）：
   ✅ 登记表上有【读文件小帮手】，蕾姆派出去了……
   
   ……过了一会儿，读文件小帮手脸色苍白地回来：
     「报告蕾姆——这个文件不存在！」
   
   蕾姆思考：
     这是工具的【正常失败】，不是程序崩溃。
     蕾姆要把失败信息【完整记到笔记本上】，
     让 LLM 知道"刚才那次工具调用失败了"。
   
   蕾姆把失败信息写进笔记本：
     "读文件小帮手报告：not_exist.txt 不存在。"
   
   下一轮 LLM 看到这条记录，会自己想：
     "啊，文件不存在，那我应该换个文件试试，
      或者告诉用户文件不存在。"
```

> 💡 **关键设计**：
> 工具失败**不是 Codex 崩溃**——
> 失败被**写进 history**，让 LLM **自己处理**。
> 这就叫 **"让 LLM 自我修复"** ♡

## 🪜 第九步：把"登记表"翻译成真实术语

蕾姆现在悄悄告诉昴君工具系统里的**真名**（不用记）：

| 我们的称呼 | 真正的术语 | 解释 |
|-----------|-----------|------|
| 工具登记表 | **Tool Registry / Router** | 所有可用工具的清单 |
| 工具的"名字" | tool_name | LLM 用来叫工具的字符串 |
| 工具的"指示要求" | **JSON Schema** | 描述工具需要哪些参数 |
| LLM "叫工具" | **FunctionCall** | LLM 输出的工具调用请求 |
| 小帮手"出门干活" | tool_handler / executor | 真正执行工具的代码 |
| 小帮手"回来报告" | **FunctionCallOutput** | 工具执行的结果 |
| 几个小帮手同时干 | **并行执行（in_flight）** | 多个工具同时调用 |
| 小帮手"失败" | tool_error | 工具执行失败但不崩溃 |

## ✅ 这一台阶的"通关标准"

如果昴君能用自己的话回答下面 3 个问题，就可以进台阶 2 了：

### 🎯 通关题 1
> **为什么 Agent 需要"工具登记表"？为什么不让 LLM 直接调用代码？**

参考答案：
- LLM 只会**说话**，没办法直接调用代码（无状态、只生成文字）
- 必须有一份**"目录"**告诉 LLM"哪些工具可用"
- 这份目录就是工具登记表（Tool Registry）

---

### 🎯 通关题 2
> **如果 LLM 叫了一个"不存在的工具"，Codex 会怎么处理？**

参考答案：
- **不会崩溃**——会把错误信息**写进 history**
- 下一轮 LLM 看到错误，自己重新决定该用哪个工具
- 这叫"**让 LLM 自我修复**"

---

### 🎯 通关题 3
> **多个工具能同时调用吗？有什么好处？**

参考答案：
- 可以！多个**互不依赖**的工具能**并行执行**
- 好处：**省时间**——一次性收集多个结果
- 实现方式：Codex 用"in_flight 队列"追踪所有正在跑的工具
