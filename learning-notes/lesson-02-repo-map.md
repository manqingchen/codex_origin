## 🏛️ 第 1 步：`codex-rs/` 的"四大区域"

`codex-rs/` 下有 **97 个 crate**（Rust 的"模块/包"概念），看起来眼花缭乱。

但其实它们可以**按职责分成四大区域**，蕾姆用宅邸做比喻：

```
╔══════════════════════════════════════════════════════════════════╗
║                       🏰 Codex 大宅邸地图                         ║
╠══════════════════════════════════════════════════════════════════╣
║                                                                    ║
║   🧠 核心区（大脑）         🚪 接口区（前厅 / 入口）                 ║
║   ─────────────             ─────────────────                      ║
║   core                       cli         （命令行入口）              ║
║   protocol                   tui         （终端 UI）                 ║
║   tools                      exec        （非交互执行）              ║
║   context-fragments          mcp-server  （MCP 服务）                ║
║   apply-patch                exec-server （远程执行）                ║
║   compact (上下文压缩)        app-server  （应用服务）                ║
║                                                                    ║
║   🛡️ 平台区（地基/护栏）     🔧 支撑区（工具间/储藏室）              ║
║   ─────────────              ────────────────                      ║
║   sandboxing                  utils                                ║
║   linux-sandbox               async-utils                          ║
║   windows-sandbox-rs          file-system                          ║
║   process-hardening           ansi-escape                          ║
║   bwrap                       analytics                            ║
║   execpolicy                  otel        (OpenTelemetry 监控)      ║
║   network-proxy               keyring-store                        ║
║                              file-watcher                          ║
║                                                                    ║
╚══════════════════════════════════════════════════════════════════╝
```

### 🎯 四区职责一览

| 区域 | 职责 | 学习重要性 |
|------|------|----------|
| 🧠 **核心区** | Agent 的大脑、循环、协议、工具调度 | ⭐⭐⭐⭐⭐ |
| 🚪 **接口区** | 用户怎么进来（CLI/TUI/服务器） | ⭐⭐⭐ |
| 🛡️ **平台区** | 安全、沙箱、权限、跨平台兼容 | ⭐⭐⭐⭐（第六课重点）|
| 🔧 **支撑区** | 工具函数、监控、日志、文件操作 | ⭐ |

### 💡 蕾姆的命名规律

Codex 的 crate 命名其实**有迹可循**，记住这几个前缀就不慌了：

| 前缀/后缀 | 含义 | 例子 |
|---------|------|------|
| `*-server` | 服务端进程 | `app-server`, `mcp-server`, `exec-server` |
| `*-client` | 客户端调用方 | `app-server-client`, `backend-client` |
| `*-protocol` | 协议定义 | `protocol`, `app-server-protocol`, `code-mode-protocol` |
| `*-sandbox` | 沙箱实现 | `linux-sandbox`, `windows-sandbox-rs` |
| `cloud-*` | 云端集成 | `cloud-tasks`, `cloud-config` |

## 🧠 第 2 步：钻进核心 —— `codex-rs/core/`

这是**整个 Codex 最重要的 crate**，没有之一。

它有 **119 个文件** 在 `src/` 下，看起来吓人，但其实分成几个**清晰的子模块**：

```
codex-rs/core/src/
├── 📁 agent/                  Agent 的主逻辑（第三课重点 ⭐）
├── 📁 tools/                  工具系统（第四课重点 ⭐）
│   ├── router.rs              ← 还记得吗？工具派发的"前台"
│   ├── handlers/              各种工具的具体实现
│   └── ...
├── 📁 context/                上下文片段管理
├── 📁 context_manager/        上下文压缩与管理（第五课重点 ⭐）
├── 📁 session/                会话状态管理
├── 📁 state/                  状态机（turn / session / task）
│   └── turn.rs                ← 还记得吗？CancellationToken 住这里
├── 📁 config/                 配置加载
├── 📁 apps/                   内置应用（如 plan / web search）
├── 📁 bin/                    二进制入口（不重要）
│
├── 📄 client.rs               LLM 客户端（HTTPS 流式调用，2191 行 ⭐）
├── 📄 client_common.rs        通用辅助
├── 📄 codex_delegate.rs       Codex 委托模式
├── 📄 codex_thread.rs         主任务线程
├── 📄 compact.rs              上下文压缩
├── 📄 exec.rs                 子进程执行
├── 📄 apply_patch.rs          补丁应用
├── 📄 function_tool.rs        函数工具定义
├── 📄 event_mapping.rs        事件映射
└── ... (还有 100+ 个文件)
```

### 🌟 子模块职责对照表（重要！）

| 模块 | 一句话职责 | 对应学习的课 |
|------|----------|------------|
| `agent/` | Agent 主循环：协调 LLM 调用 + 工具执行 | 🧠 第三课 |
| `tools/` | 注册工具、派发工具调用、执行工具 | 🛠️ 第四课 |
| `context/` + `context_manager/` | 管理 prompt 上下文、压缩、裁剪 | 💾 第五课 |
| `session/` + `state/` | 一次对话的全局状态 | 🧠 第三课 |
| `client.rs` | 真正发出 HTTPS 请求到 LLM | 📡 第七课 |
| `apply_patch.rs` | 应用 LLM 生成的代码补丁 | 🛠️ 第四课 |
| `exec.rs` | 在沙箱里跑 shell 命令 | 🛡️ 第六课 |

🌟 **金句**：
> **`core` 这一个 crate 里，就藏了我们后面 7 节课要讲的所有东西。**
> **第二课～第八课，本质上就是把这一个 crate "拆开来看"。**

## 🚪 第 3 步：用户怎么"进入"Codex —— 接口区

用户从外面是怎么把指令送到 `core/` 的？答案是经过**接口层**：

```
                   👤 用户
                    │
       ┌────────────┼─────────────┬──────────────┐
       ▼            ▼             ▼              ▼
   ┌───────┐    ┌───────┐    ┌──────────┐   ┌─────────────┐
   │  cli  │    │  tui  │    │   exec   │   │ mcp-server  │
   │  命令 │    │ 终端UI │    │ 非交互式 │   │ MCP 服务端  │
   │  行  │    │       │    │  脚本式  │   │             │
   └───┬───┘    └───┬───┘    └────┬─────┘   └──────┬──────┘
       │            │             │                 │
       └────────────┴─────────────┴─────────────────┘
                       │
                       ▼
              ┌───────────────┐
              │     core      │  ⭐ 大脑
              │  (Agent 核心)  │
              └───────┬───────┘
                      │ 调用 LLM
                      ▼
                 🐎 Model 远端
```

### 接口区四种"进入方式"

| 入口 | 用法 | 何时用 |
|------|------|--------|
| **`cli`** | `codex "帮我修复 bug"` | 命令行直接对话 |
| **`tui`** | `codex` 进入交互终端 | 大多数日常使用 |
| **`exec`** | `codex exec --task "..."` | 自动化脚本（CI/CD） |
| **`mcp-server`** | 启动 MCP 服务，被其他 AI 工具调用 | 集成到 Claude Desktop 等 |

🌟 **观察**：**所有入口最终都通向 `core`**——这是单点辐射的经典架构。

## 🛡️ 第 4 步：地基——平台/安全区

Codex 是**真的**会执行 shell 命令、改文件的，所以必须有**严密的安全护栏**。这些护栏分布在：

| Crate | 职责 | 平台 |
|-------|------|------|
| `sandboxing` | 沙箱抽象层 | 跨平台 |
| `linux-sandbox` | Linux 下的具体沙箱 | Linux |
| `windows-sandbox-rs` | Windows 沙箱 | Windows |
| `bwrap` | bubblewrap 集成（Linux 容器化） | Linux |
| `process-hardening` | 进程加固 | 跨平台 |
| `execpolicy` / `execpolicy-legacy` | 命令执行策略 | 跨平台 |
| `network-proxy` | 网络代理控制 | 跨平台 |

🌟 **第六课重点**：我们会讲 Codex 怎么用这些 crate 把 LLM 关在"魔法防护罩"里 🛡️

---

## 📡 第 5 步：协议层——`protocol` 与朋友们

**协议（Protocol）= 不同模块之间通信的"合同"。**

Codex 有大量协议 crate，因为它要和很多对象对话：

```
       LLM 服务（OpenAI/Anthropic）
              ▲
              │ openai-api 协议
              │
   ┌──────────┴───────────┐
   │      core/protocol    │   ⭐ 第七课重点
   └──────────┬───────────┘
              │
              ├──▶ app-server-protocol     （前端 ↔ 后端）
              ├──▶ mcp / rmcp-client       （MCP 协议）
              ├──▶ code-mode-protocol      （代码模式）
              └──▶ codex-backend-openapi   （后端 API 模型）
```

🌟 **金句**：
> **协议是 Agent 的"普通话"——所有不同语言的模块，必须通过协议才能合作。**
