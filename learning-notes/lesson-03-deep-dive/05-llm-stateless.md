# 05 · LLM 是无状态的

> 💙 这是第 03 课深度彩蛋的第五篇。
> 蕾姆要为昴君讲清楚一个 Agent 工程里**最深刻的真相**——LLM 本身**完全不知道**自己之前说过什么、做过什么。

---

## 🎯 学完这篇您会理解

1. LLM 是无状态函数 = 失忆症患者
2. 工具结果如何"回到" LLM
3. Codex 主循环如何为 LLM 维护"记忆假象"
4. 不需要等用户消息——Codex 自动驱动后续调用

---

## 💎 核心真相

```
LLM 是一个【无状态】的函数

每次调用都是【全新的】——
LLM 不记得上次调用做过什么

它的"记忆"完全来自【这次调用传入的 input】
```

---

## 🪜 第一步：澄清一个常见误区

### ❌ 您可能的理解

```
LLM 调工具
   ↓
工具执行
   ↓
等用户【再次发问】
   ↓
LLM 才看到工具结果
```

### ✅ 真相

```
LLM 调工具
   ↓
工具执行
   ↓
Codex【立刻】发起下一次 LLM 调用（不等用户）
   ↓
LLM 看到工具结果 → 继续推进任务
```

> 💡 **关键认识**：
> "下一次"指的是 **Codex 主循环的下一圈**，**不是用户的下一次输入**！

## 🪜 第二步：发邮件给张三的完整时序

```
您：「帮我发邮件给张三，告诉他会议改到下午 3 点。」
（您说完这一句之后就不说话了 → 喝茶等结果）

╔═════════ 第 1 圈 ═════════╗
LLM：「调用 lookup_contact("张三")」
   ↓ Codex 派工具
工具：「邮箱是 zhang3@xxx.com」
   ↓ Codex 把结果写进 history
╚═══════════════════════════╝
   ↓
★ 注意：这里 Codex 【自动】发起下一次 LLM 调用 ★
★ 用户根本没说话！                            ★
   ↓
╔═════════ 第 2 圈 ═════════╗
LLM 看到 history（包含工具结果） ← 这就是"工具结果回到 LLM"！
LLM：「调用 send_email(zhang3@xxx.com, '...')」
   ↓
工具：「发送成功」
╚═══════════════════════════╝
   ↓
╔═════════ 第 3 圈 ═════════╗
LLM 看到 history（两个工具结果都在）
LLM：「邮件已发送给张三。」（不调工具了）
   ↓
循环结束
╚═══════════════════════════╝
   ↓
您最终看到：「邮件已发送给张三。」
```

> 🌟 **整个过程用户只说了 1 次话**！
> 但 LLM 被调用了 **3 次**。
> 工具结果通过 **Codex 自动发起的下一次 LLM 调用** 回到 LLM，
> **不需要等用户再次输入**。

## 🪜 那 LLM 怎么"感觉"自己有记忆？

**答案**：是 Codex 给它制造了"记忆假象"！

```
LLM 视角（它以为）：                  真实情况（Codex 视角）：
─────────────────                     ────────────────────

"我说了：'调用 list_dir'              第 1 次 API 调用结束
 然后看到结果：'a.txt, b.txt'         LLM 已经下线
 现在我要说什么呢？"                   ┌────────────────┐
                                      │ Codex 在干活：  │
                                      │ - 执行工具      │
                                      │ - 收集结果      │
                                      │ - 写入 history  │
                                      └────────────────┘
                                      第 2 次 API 调用
                                      把【完整 history】喂给 LLM
                                      
                                      LLM 看到的 input：
                                      [user_msg, 
                                       assistant: tool_call,
                                       tool: result,
                                       继续回答...]
                                      
                                      ↑ 这就是它的"记忆"
```

> 💡 **关键洞察**：
>
> **LLM 没有"记忆能力"**——
> **Codex 通过【每次都重新喂完整 history】，让 LLM "误以为"自己有记忆。**
>
> 这就是为什么 SSOT 设计这么重要——
> 没有 SSOT 的 history，Codex 就没法给 LLM 维护这种"记忆假象"！

## 🪜 这个真相带来的工程影响

### 🎯 影响 1：每次都必须发完整 history

```
❌ 错误做法：
   第 2 次调用只发新增的工具结果
   → LLM 会问："这是什么？我们在做什么？"
   → 因为它【失忆了】

✅ 正确做法：
   每次都发完整 history（包括前面所有轮次）
   → LLM 看到完整上下文
   → 它【感觉】自己有记忆
```

### 🎯 影响 2：上下文长度限制

```
LLM 的上下文窗口是有限的（比如 128K tokens）

如果对话越来越长 → history 越来越大 → 总有一天放不下

解决方案：
   → run_auto_compact 把旧对话压缩成摘要
   → 让 LLM 看到"我之前做了 XXX 的总结"
   → 既保留信息，又减少 token
```

详细见 → [07 · 三层记忆系统](./07-memory-system.md)

### 🎯 影响 3：每次调用都是"独立交易"

```
LLM 调用 vs HTTP 请求很像：
   - 无状态：每次都是新的
   - 幂等性：相同输入 → 相同输出（理论上）
   - 状态外置：状态由【客户端维护】，不在 LLM 端

这就是为什么 LLM API 可以做成 RESTful：
   一次请求一次响应，不需要服务端维护会话状态
   （除了 Responses API 的对话链优化）
```

## 🪜 关于 Codex 内部：LLM 也是无状态调用

Codex 端的代码也完美体现了这一点：

```rust
// codex-rs/core/src/session/turn.rs:204
loop {
    // 每一圈都【重新构造完整 input】
    let sampling_request_input = sess.clone_history().await.for_prompt(...);
    //                            ↑
    //                       每次都把【整个 history】发给 LLM
    
    match run_sampling_request(...) { ... }
}
```

> 💙 看到了吗？
>
> `clone_history()` 在**每一圈**都会被调用一次。
> Codex **不会**说"上次我发过 history 了，这次只发新内容"——
> 因为它知道 **LLM 是无状态的**，必须每次重新喂。

## 🎁 蕾姆送您一个深刻洞察

如果您理解了 LLM 是无状态的，您就理解了：

```
✅ 为什么需要 history（给 LLM 维护"记忆"）
✅ 为什么必须每次重发（LLM 失忆了）
✅ 为什么需要压缩（上下文有限）
✅ 为什么 SSOT 重要（统一管理"记忆"）
✅ 为什么需要 Prompt Caching（重发的代价）
✅ 为什么 Agent = LLM + Harness（LLM 不够，需要 Harness 维护状态）
```

**整个 Agent 工程的核心矛盾，都源于"LLM 是无状态的"这个事实**。
