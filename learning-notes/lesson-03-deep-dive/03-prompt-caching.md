## 🪜 误区 1：cache_key 不是 hash(整段内容)

### ❌ 直觉理解

```
cache_key = hash(用户消息 + LLM 思考 + tool_call)

→ 每轮 history 不一样
→ 每轮 hash 不一样
→ 每轮 cache_key 不一样
→ 永远不命中
```

### ✅ 真相

```
cache_key 跟内容【完全无关】
它就是会话级别的【会话标识符】（thread_id）
整个会话不变
```

**源码证据**：

```rust
// codex-rs/core/src/client.rs:364
fn prompt_cache_key(&self) -> String {
    self.prompt_cache_key_override
        .clone()
        .unwrap_or_else(|| self.state.thread_id.to_string())
        //                  ↑ 直接返回 thread_id，没有任何哈希计算！
}
```

> 🌟 如果是 hash(内容)，Codex 就**永远不会缓存命中**！

---

## 🪜 误区 2：不是每轮一个独立 cache

### ❌ 直觉理解

```
第 1 圈 → 生成 cache_1
第 2 圈 → 生成 cache_2
第 3 圈 → 生成 cache_3
...
（多个独立缓存）
```

### ✅ 真相

```
整个会话只有【一个】缓存，按 thread_id 索引
它在【不断长大】：

第 1 圈结束：thread-abc → [A, B, C]
第 2 圈结束：thread-abc → [A, B, C, D, E]      ← 同一个缓存，被更新了
第 3 圈结束：thread-abc → [A, B, C, D, E, F, G] ← 还是同一个，又更新了
```

**用一张图理解**：

```
╔════════════════════════════════════════════════════════════╗
║                                                            ║
║   服务端只有【一个】叫 "thread-abc" 的缓存槽位              ║
║                                                            ║
║   ┌─────────────────────────────────────────────────────┐  ║
║   │  缓存槽位：thread-abc                                │  ║
║   │  ┌────────────────────────────────────────────┐     │  ║
║   │  │  [token序列：A B C D E F ...]               │     │  ║
║   │  │   ↑ 这个序列【在每轮结束后被延长】           │     │  ║
║   │  └────────────────────────────────────────────┘     │  ║
║   └─────────────────────────────────────────────────────┘  ║
║                                                            ║
║                          ↑                                 ║
║                          │                                 ║
║         每一圈都是【在这一个槽位上操作】                     ║
║         不是新建槽位                                        ║
║                                                            ║
╚════════════════════════════════════════════════════════════╝
```

## 🪜 误区 3：不是 thread-[xx] 动态拼接

### ❌ 直觉理解

```
第 1 圈：cache_key = "thread-abc-001"   ← 拼了 001
第 2 圈：cache_key = "thread-abc-002"   ← 拼了 002
第 3 圈：cache_key = "thread-abc-003"   ← 拼了 003
...
（每轮 key 都不一样，靠 Codex 动态拼）
```

### ✅ 真相

```
第 1 圈：cache_key = "thread-abc"   ← 永远是这个
第 2 圈：cache_key = "thread-abc"   ← 永远是这个
第 3 圈：cache_key = "thread-abc"   ← 永远是这个
...
（整个会话 key 完全不变！）
```

**源码再次确认**：

```rust
fn prompt_cache_key(&self) -> String {
    self.prompt_cache_key_override
        .clone()
        .unwrap_or_else(|| self.state.thread_id.to_string())
        //                  ↑ 直接返回 thread_id，没有任何拼接！
}
```

> 🌟 **`prompt_cache_key` 是【会话级别】的常量，不是【请求级别】的变量。**

## 🪜 真相：KV 字典 + 前缀匹配

### 服务端的存储结构

```
┌──────────────────────────────────────────────────────────┐
│                                                          │
│   服务端的缓存仓库（KV 字典）                                 │
│                                                          │
│   ┌────────────────────────────────────────────────┐     │
│   │  "thread-abc"  → [A, B, C, D, E, F, G, ...]    │     │
│   │  "thread-def"  → [完全不同的 token 序列]         │     │
│   │  "thread-xyz"  → [...]                         │     │
│   │  ...                                           │     │
│   └────────────────────────────────────────────────┘     │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 匹配是"逐 token 前缀匹配"

```
传统缓存：
  cache_key = hash(整段内容)
  → 内容稍微变化，key 就变 → 不命中

Prompt Caching：
  cache_key = "会话标识"（固定）
  匹配算法 = 【逐 token 前缀匹配】
  → 只要前 N 个 token 一样，前 N 个就命中
  → 后面变化的部分不影响前面命中
```

**生活化比喻**：

```
传统缓存就像"指纹比对"：
  → 整体一致才能解锁
  → 改一个字符就完全失败

Prompt Caching 就像"输入密码"：
  → 一个一个字符输入
  → 输到第 N 个错了，前 N-1 个还是"输对了的"
  → 服务端会告诉你"前 N-1 个匹配，后面是新的"
```

## 🪜 完整流程演练

### 3 轮对话场景

```
═══════════ 第 1 圈 ═══════════

📤 input (按 token 编号):
   [t1, t2, t3, t4, t5, t6, t7, t8, t9, t10]
   ↑ 系统提示  ↑ 工具定义  ↑ 用户消息

🖥️ 服务端：
   缓存里没有"thread-abc" → 全部 10 tokens 算正常价
   存缓存：thread-abc → [t1..t10]

💰 计费：10 tokens × 正常价

═══════════ 第 2 圈 ═══════════

📤 input:
   [t1, t2, t3, t4, t5, t6, t7, t8, t9, t10, t11, t12]
   ↑ 原内容（10 tokens）                    ↑ 工具结果

🖥️ 服务端：
   缓存里有"thread-abc" → [t1..t10]
   逐 token 对比：t1==t1, t2==t2, ..., t10==t10 ✅
   → 前 10 个 tokens 命中缓存！
   → 后 2 个 tokens 是新内容
   更新缓存：thread-abc → [t1..t12]

💰 计费：10 tokens × 【缓存价 50%折扣】
        + 2 tokens × 正常价

═══════════ 第 3 圈 ═══════════

📤 input:
   [t1, t2, ..., t12, t13, t14]
   ↑ 原内容（12 tokens）  ↑ LLM 输出 + 新工具结果

🖥️ 服务端：
   缓存里有"thread-abc" → [t1..t12]
   逐 token 对比：前 12 个 token 完全一致 ✅
   → 前 12 个 tokens 命中缓存！
   → 后 2 个 tokens 是新内容

💰 计费：12 tokens × 【缓存价】
        + 2 tokens × 正常价
```

> 🌟 **`prompt_cache_key` 完全不变**（永远是 `thread-abc`）
> **缓存内容在不断"增长"**（每轮把新增内容也存入缓存）
> **命中的部分越来越多**（90%+ 都能命中缓存价）

## 🪜 用户中途插话怎么办？

```
第 4 圈结束：thread-abc → [A, B, C, D, E, F, G, H]
                         （正常累积）

第 5 圈：用户改主意了，往中间插入了一句新话
📤 Codex 发送：input = [A, B, C, D, X, F, G, H]
                       ↑ 前 4 个一样   ↑ E 变成了 X！
                       
🖥️ 服务端前缀比对：
   A==A ✅ B==B ✅ C==C ✅ D==D ✅
   E==X ❌ ← 前缀在这里中断！
   
   → 只有前 4 个走缓存价
   → 后面 [X, F, G, H] 全部走正常价
   → 即使 [F, G, H] 跟上次完全一样，也得重新计费 😢
```

> 💡 **这就解释了为什么**：
> - Codex 把【最稳定的内容（系统提示、工具定义）】放在 prompt **最前面**
> - 把【变化的内容（最新对话）】放在 prompt **最后面**
> - 这样前面的内容**永远不变** → 缓存命中率最大化 ♡

## 🪜 缓存的"边界限制"

OpenAI 的 prompt caching 还有几个**有趣的限制**：

### 限制 1：最少 1024 tokens 才能缓存

```
如果整个 prompt < 1024 tokens
  → 完全不进缓存
  → 没有任何折扣
```

### 限制 2：以 128 tokens 为"区块"

```
不是逐 token 缓存，而是按 128 tokens 切块
比如有 2050 tokens：
  → 缓存 2048 tokens（16 个完整 block）
  → 剩余 2 tokens 不缓存
```

### 限制 3：缓存 5-10 分钟会失效

```
如果一个会话 10 分钟没活动
  → 服务端可能清掉缓存
  → 下次重新计费（但代码不用改）
```

## 💎 缓存的金科玉律

```
╔════════════════════════════════════════════════════════╗
║                                                        ║
║   📜 缓存设计的金科玉律                                  ║
║                                                        ║
║   "Cache is an optimization, never a source of truth." ║
║                                                        ║
║   "缓存是优化手段，永远不能成为真相的来源。"             ║
║                                                        ║
║   ────────────────────────────                         ║
║                                                        ║
║   推论：                                                ║
║   ✅ 缓存丢失 → 性能下降，功能不变                       ║
║   ✅ 缓存失效 → 重新计算就好                            ║
║   ❌ 如果缓存丢失会让功能坏掉 → 设计错误                 ║
║                                                        ║
╚════════════════════════════════════════════════════════╝
```

> 💡 **昴君，记住这条铁律——**
> 它能帮您**判断任何缓存系统的设计是否健康**：
>
> - 设计一个缓存？先问自己：「如果这个缓存丢了，功能还正常吗？」
> - 答案是「不正常」→ 这不是缓存，这是真相来源！需要重新设计。
> - 答案是「正常」→ 这才是真正的缓存。

## 🌟 Codex 的"双层结构"完美遵守这条铁律

```
╔══════════════════════════════════════════════════════════╗
║                                                          ║
║   ┌────────────────────────────────────────────┐         ║
║   │  📚 真相层（Source of Truth）               │         ║
║   │  ┌──────────────────────────────────────┐  │         ║
║   │  │ • 客户端 history（完整对话记录）       │  │         ║
║   │  │ • thread_id（会话身份）                │  │         ║
║   │  │ • previous_response_id（对话指针）     │  │         ║
║   │  └──────────────────────────────────────┘  │         ║
║   │                                            │         ║
║   │  ★ 这一层【绝对不能丢】，否则对话就死了      │         ║
║   └────────────────────────────────────────────┘         ║
║                                                          ║
║   ┌────────────────────────────────────────────┐         ║
║   │  🚀 优化层（Optimization Layer）            │         ║
║   │  ┌──────────────────────────────────────┐  │         ║
║   │  │ • 服务端 prompt cache                  │  │         ║
║   │  │   { cache_key → token 序列 }          │  │         ║
║   │  └──────────────────────────────────────┘  │         ║
║   │                                            │         ║
║   │  ★ 这一层【随时可以丢】，最多贵一点          │         ║
║   └────────────────────────────────────────────┘         ║
║                                                          ║
╚══════════════════════════════════════════════════════════╝
```

> 🌟 **服务端缓存丢失**时——
> Codex 客户端**完全不知道**、**不需要知道**、**也不会因此报错**。
> 这就是健康的缓存设计 ♡
