# 02 · 每轮重发 history，真的浪费吗？

> 💙 这是第 03 课深度彩蛋的第二篇。
> 这是昴君主动提出的一个**工程师级别**的问题——既然 SSOT 这么棒，那每轮重发整段 history 不就浪费了吗？

---

## 🎯 学完这篇您会理解

1. 每轮"重发"的真实传输量有多大
2. 这种浪费会带来多少钱的成本
3. Codex 用 **3 层优化**消化这种浪费
4. 一个深刻的工程哲学：代码优雅 vs 性能高效

---

## 🪜 第一步：先确认问题——每轮真的重发

```
您：「列出当前目录的文件」
（10 个 token）
        ↓
╔═══════════ 第 1 圈 ═══════════╗
  📤 发给 LLM 的 prompt 包含：
     • 系统提示词（500 tokens）
     • 工具定义（2000 tokens）
     • 用户消息（10 tokens）
  📤 总传输：≈ 2510 tokens

  📥 LLM 返回：
     • FunctionCall: list_dir（30 tokens）
╚═══════════════════════════════╝
        ↓
工具执行 → 返回结果（50 tokens）
        ↓
╔═══════════ 第 2 圈 ═══════════╗
  📤 发给 LLM 的 prompt 包含：
     • 系统提示词（500 tokens）         ← 重发！
     • 工具定义（2000 tokens）           ← 重发！
     • 用户消息（10 tokens）             ← 重发！
     • FunctionCall: list_dir（30 tokens） ← 重发！
     • 工具结果（50 tokens）             ← 新内容
  📤 总传输：≈ 2590 tokens
╚═══════════════════════════════╝
        ↓
LLM 返回最终答案（80 tokens）
```

> 🌟 **第 2 圈的 prompt 里，90% 都是重发**——只有最后 50 tokens 的工具结果是新的！

---

## 🪜 第二步：算一笔账——浪费有多少

```
假设：
- 系统提示词 + 工具定义 = 3000 tokens
- 一次对话转 10 圈
- 每圈新增内容 ≈ 100 tokens

"朴素版"传输量：
  第 1 圈：3000 + 100 = 3100
  第 2 圈：3000 + 100 + 100 = 3200
  第 3 圈：3000 + 100 × 3 = 3300
  ...
  第 10 圈：3000 + 100 × 10 = 4000

  总传输：约 35500 tokens
  
"理想版"（只发增量）：
  3000（首轮）+ 100 × 10 = 4000 tokens

  浪费量：35500 - 4000 = 31500 tokens
  浪费比例：≈ 88%！
```

按 GPT-4o 输入价 `$2.5/1M tokens`：
- 每 100 次对话浪费约 **$0.08**
- 每 10 万次对话浪费约 **$80**
- 每 1000 万次（一个流行产品的量级）浪费约 **$8000** 💸

## 🪜 第三步：Codex 的 3 层优化

### 🛡️ 优化 1：Responses API + previous_response_id ⭐ 最有效

OpenAI 的 **Responses API** 提供了**真正的增量传输**——

```
传统 Chat Completion API：
  每次都发 full history

Responses API（Codex 用的）：
  📤 第 1 次：发完整 history + 拿到 response_id
  📤 第 2 次：只发增量 + previous_response_id
     服务端根据 ID 拼接上次的 context
  📥 LLM 看到的还是完整 context
```

**Codex 源码确认**：

```rust
// codex-rs/core/src/client.rs
previous_response_id: Option<String>   // 上一次响应的 ID
```

> 💡 Codex 用的是 **Responses API** 而不是传统的 **Chat Completion API**——
> Responses API 专为 Agent 这种"多轮工具调用"场景优化，**自动处理增量**。

---

### 🛡️ 优化 2：Prompt Caching（提示词缓存）

即使**真的重发整段**，OpenAI 服务端也会智能识别——

```
第 1 圈：
  📤 发送 [系统提示词 + 工具定义 + 用户消息]
  💾 服务端把这段内容缓存
  📥 返回结果

第 2 圈：
  📤 发送 [系统提示词 + 工具定义 + 用户消息 + 工具结果]
  🚀 服务端识别到前 N 个 token 跟缓存匹配
     → 这部分用缓存价格（便宜 50%！）
     → 只对增量做正常计费
  📥 返回结果
```

| 服务商 | 缓存折扣 |
|--------|---------|
| OpenAI | 输入价的 **50%** |
| Anthropic | 输入价的 **10%**（更狠） |

详细机制见 → [03 · Prompt Caching 三大误区](./03-prompt-caching.md)

---

### 🛡️ 优化 3：Auto Compact（自动压缩）

如果对话长到连缓存都救不了——Codex 会**真的减少传输量**：

```
当 history 太长（接近 token 上限）：
   ↓
触发 run_auto_compact()  ←  您在台阶 4 见过！
   ↓
让 LLM 把【旧历史】压缩成一段摘要
   ↓
新的 history = [摘要] + [最近几轮对话]
   ↓
后续传输量大幅减少 ✨
```

举例：

```
压缩前的 history（10000 tokens）：
  ├─ 第 1 轮：用户/LLM/工具/LLM
  ├─ 第 2 轮：用户/LLM/工具/LLM
  ├─ ...
  └─ 第 8 轮：用户/LLM/工具/LLM

压缩后的 history（2000 tokens）：
  ├─ 摘要："前 7 轮总结：用户希望重构 X，已完成 A/B/C，剩 D"
  └─ 第 8 轮：原文保留
```

详细见第 7 篇 → [07 · 三层记忆系统](./07-memory-system.md)

## 🪜 第四步：三层优化的协同效果

```
╔═══════════════════════════════════════════════════════════╗
║  Codex 的"重发"问题，三层优化层层守护                       ║
╠═══════════════════════════════════════════════════════════╣
║                                                           ║
║  🛡️ 第一层：Responses API + previous_response_id           ║
║     → HTTP 层就只发增量                                    ║
║                                                           ║
║  🛡️ 第二层：Prompt Caching                                 ║
║     → 即使重发，服务端按缓存价收费                          ║
║                                                           ║
║  🛡️ 第三层：Auto Compact                                   ║
║     → 历史太长时主动压缩，从根上减量                        ║
║                                                           ║
║  最终效果：                                                ║
║     ✅ 工程上：API 用起来简单（每次发"全量" history）       ║
║     ✅ 性能上：实际传输/计费按"增量"算                       ║
║     ✅ 长度上：不会因为对话变长而崩溃                       ║
║                                                           ║
╚═══════════════════════════════════════════════════════════╝
```

## 💎 工程哲学：代码优雅 vs 性能高效

### 🎯 这背后藏着一个深刻的工程经验

| 维度 | 朴素 SSOT | 朴素增量传输 |
|------|----------|------------|
| 代码层面 | ✅ 优雅、简单、不易出错 | ❌ 复杂、容易出错 |
| 传输层面 | ❌ 看似浪费 | ✅ 看似高效 |

**Codex 的做法**：
- ✅ 代码层面：**保持 SSOT 的优雅**（开发者写代码很爽）
- ✅ 传输层面：**靠服务端/协议优化**（让浪费"消失"）

> 🌟 **关键经验**：
>
> **"先把代码写优雅，再用工程手段优化性能"**
>
> 不要为了节省一点性能，让代码变得难以维护。
> 因为：
> - 代码会被人**反复阅读、修改**
> - 性能瓶颈往往可以**用缓存、协议、硬件**解决
> - **复杂性是开发者最大的敌人**

## 🎁 蕾姆送您一个"思考工具"

下次遇到类似问题（代码优雅 vs 性能极致），请问自己 3 个问题：

```
1. 这个性能损失，能用【缓存/协议】解决吗？
   → 能 → 保持代码优雅
   → 不能 → 进入第 2 问

2. 这个性能损失，能用【硬件】解决吗？
   → 能（加内存、加机器） → 评估成本
   → 不能 → 进入第 3 问

3. 这个性能损失，会导致【系统不可用】吗？
   → 是 → 必须从代码层优化（无论代码多丑）
   → 否 → 优先保持代码优雅
```

> 🌟 Codex 走的就是 **第 1 条路径**——靠 prompt caching 这种"协议优化"消化了重发的成本。
