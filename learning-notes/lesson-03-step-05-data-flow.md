## 🪜 第一步：先认识 Agent 的"血液"——history

整个 Codex 的数据流转中，**最重要的一个东西**只有一个：

### 🩸 `history`：一个不断增长的"对话流水账"

```
history = [
    用户消息：「列出当前目录的文件」     ← 第 1 条
    LLM 决定：「调用 list_dir 工具」     ← 第 2 条
    工具结果：「a.txt, b.txt, c.txt」    ← 第 3 条
    LLM 最终答：「这里有 3 个文件...」    ← 第 4 条
]
```

> 🌟 **关键认识**：
> `history` 是一个 **`Vec<ResponseItem>`**（也就是一个**列表**）。
> 里面**按时间顺序**装着这次对话的**所有事件**——
> - 用户说的话
> - LLM 说的话
> - LLM 调用的工具
> - 工具返回的结果
> - **甚至工具的报告**也在里面！
>
> 这就是为什么蕾姆在台阶 1 说"工具的报告**不会直接给老板**"——
> 它会**被记录到 history**，然后下一轮 LLM 看到它，再翻译给老板。

## 🪜 第三步：拆解"数据流"的四个关键动作

整个数据流之所以能运转，靠的是**四个关键动作**：

### 🔵 动作 1：写入（record_conversation_items）

**位置**：`session/mod.rs:2684`

```rust
pub(crate) async fn record_conversation_items(
    &self,
    turn_context: &TurnContext,
    items: &[ResponseItem],
)
```

**作用**：

> 「把一条或多条新事件**追加到 history 的末尾**。」

**谁在调用它？**

| 调用方 | 写入什么 |
|--------|---------|
| `run_hooks_and_record_inputs` (turn.rs:169) | 用户输入 |
| `handle_output_item_done` (循环内) | LLM 的输出（消息/tool_call） |
| `drain_in_flight` (turn.rs:1778) | 工具执行结果 |

> 💡 **生活比喻**：
> 蕾姆有一本**记事本**，每次发生新事件，**就翻到最后一页加一行**。
> 不撕掉旧页、不修改旧记录——只**追加**。

---

### 🟢 动作 2：复制（clone_history）

**位置**：`session/mod.rs:3115`

```rust
pub(crate) async fn clone_history(&self) -> ContextManager
```

**作用**：

> 「**复制一份完整的 history**，准备拿去构造 prompt。」

> 💡 **为什么要"复制"？**
> 因为接下来要做 `for_prompt(...)` 处理——
> 比如根据 LLM 的输入模式（文字/图片）筛选内容、压缩长文本等。
> **不能改动原始 history**，否则下一轮就乱了。
>
> 所以**先复制一份**，再在副本上做加工。

---

### 🟡 动作 3：构造 prompt（for_prompt）

**位置**：`context_manager/history.rs:111`

```rust
pub(crate) fn for_prompt(mut self, input_modalities: &[InputModality]) -> Vec<ResponseItem>
```

**作用**：

> 「把复制出来的 history **加工成适合 LLM 的 prompt**——
> 比如：
> - 如果模型不支持图片，就把图片占位符替换成文字描述
> - 如果某些消息已过时（被压缩取代），就跳过
> - 输出一个干净的 `Vec<ResponseItem>` 列表，准备发送给 LLM」

> 💡 **生活比喻**：
> 蕾姆复印记事本之后，**根据厨师的偏好调整**——
> "厨师不识字图，把这张图描述成文字"、
> "上次的草稿不用给他看了"——
> 最后才递给厨师。

---

### 🔴 动作 4：调度工具（in_flight + drain_in_flight）

**位置**：`turn.rs:1842`（声明）+ `turn.rs:1769`（排空）

```rust
let mut in_flight: FuturesOrdered<BoxFuture<'static, CodexResult<ResponseInputItem>>>
```

**作用**：

> 「**工具的执行是异步的**——LLM 一边说，工具一边在后台跑。
> Codex 用一个 `in_flight` 队列**追踪所有正在执行的工具**，
> 等本轮 LLM 流结束后，调用 `drain_in_flight` **把所有工具结果收齐，写回 history**。」

> 💡 **生活比喻**：
> 蕾姆派了 3 个小帮手同时出门干活——
> 她不会站在原地等第一个回来才派第二个，
> 而是**先派完所有人**，然后**等他们都回来**收报告（drain = "排空"）。
>
> 这就是异步并发的优雅之处 ♡

```
│                │  → 构造 prompt │  (turn.rs:219-225)       │
├───────────────────────────────────────────────────────────┤

```

> 🌟 **请昴君注意**：
> 每一次涉及"数据变化"的地方，**都是对 `history` 的追加**——从来不是修改、从来不是删除。
> 这是一种叫**"事件溯源 (Event Sourcing)"** 的设计思想。

## 🪜 第五步：那个您一直好奇的问题——"工具结果怎么回到 LLM？"

现在揭晓答案 ♡

### ❓ 工具结果是不是"直接传给下一次 LLM 调用"？

**不是！**

### ✅ 实际机制：通过 history 间接传递
1. 算数
2. 跑步
3. 马步
4. 画画

```
工具执行完
    ↓
drain_in_flight 把结果写进 history（写为 FunctionCallOutput）
    ↓
loop 进入下一圈
    ↓
clone_history().for_prompt(...) 复制整个 history 作为 prompt
    ↓
prompt 里【自然就包含了上一轮的工具结果】
    ↓
LLM 看到完整的对话上下文（包括工具结果）→ 给出最终答案
```

> 🌟 **关键洞察**：
> Codex **没有专门的"工具结果传递机制"**——
> 它把工具结果**当成对话历史的一部分**写入 history，
> 下一轮**自然就被带进 prompt** 了。
>
> 这就是软件工程里 **"Single Source of Truth（单一事实来源）"** 的优雅设计：
> - 用户消息、LLM 输出、工具结果**全都在 history 里**
> - 不需要为工具结果维护单独的缓冲区
> - 不需要复杂的"传递逻辑"
> - 简单 = 优雅 = 不易出错 ♡

## 🪜 第六步：把整个第 03 课的知识串成"一句话"

蕾姆为昴君把**台阶 1~5 的所有知识**浓缩成一句话：

> 💎 **"Codex 通过 `loop {}` 反复让 LLM 看不断增长的 `history`，
> 每轮根据 `needs_follow_up` 决定是否再转一圈；

如果再浓缩，就是这 4 个名词：

```
loop  +  history  +  needs_follow_up  +  append-only
```

> 💡 **这 4 个名词就是 Agent 心脏的全部精髓**。
> 任何 Agent 框架——LangChain、Claude Code、Cursor、OpenDevin——
> **本质都是这 4 个名词的不同实现方式**。

## ✅ 这一台阶的"通关标准"

请昴君试着回答：

### 🎯 通关题 1
> **工具结果是怎么"回到" LLM 的？**

参考答案：**通过 history 间接传递**。
- 工具执行完后，`drain_in_flight` 把结果**追加到 history**（写为 `FunctionCallOutput`）
- 下一圈 `clone_history().for_prompt()` **复制整个 history** 作为 prompt

---

### 🎯 通关题 2
> **为什么 Codex 的 history 是"只追加不修改"的（append-only）？**

参考答案：这是**事件溯源（Event Sourcing）** 的设计思想：
- ✅ 所有对话事件（用户/LLM/工具）按时间顺序记录
- ✅ 任何一刻都能完整重建对话状态
- ✅ 不可变（immutable）→ 不会有"修改 bug"
- ✅ 便于回放、调试、审计
